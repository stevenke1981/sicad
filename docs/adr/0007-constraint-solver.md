# 0007：約束求解採用既有求解器（planegcs 或 libslvs），不自行開發

- **狀態**：Accepted（方向已定；兩個候選之間的最終選擇待評估，結果將以新 ADR 記錄）
- **日期**：2026-11-17
- **決策者**：專案負責人
- **影響範圍**：Rust core 的約束圖、求解器整合層、第 3 階段工作項目

## 背景

`CadDocument 1.0` 沒有約束的概念：所有位置都是絕對座標（孔的 `x`／`y`／`z`），「四角孔離邊 10」這類設計意圖在規劃階段就被展開成數字，之後修改板長並不會連帶移動孔位。

CadDocument 2.0（[`../CONCEPT_DIMENSIONAL_LADDER.md`](../CONCEPT_DIMENSIONAL_LADDER.md)）讓元件透過 port 與約束連接。要讓「agent 宣告關係、系統算出位置」成立，需要幾何約束求解器：給定一組幾何實體與約束（重合、平行、垂直、距離、角度、相切等），求出滿足約束的參數值，並回報欠約束、過約束與衝突。

幾何約束求解是專門領域：非線性方程組的數值求解、自由度分析、冗餘與衝突診斷、對初始值的敏感度，都需要長期累積才會穩健。這不是本專案的差異化所在。

## 決策

1. **不自行撰寫約束求解器**，採用既有、經長期實際使用驗證的開源求解器。
2. 候選限定為兩者，並**進行對照評估**後擇一：
   - **planegcs**：FreeCAD Sketcher 所使用的 2D 幾何約束求解器，已有可在瀏覽器與 Node 執行的 WebAssembly 建置。
   - **SolveSpace libslvs**：SolveSpace 的約束求解函式庫，支援 2D 草圖與 3D 空間中的點、線、平面等實體的約束。
3. Rust core 擁有約束圖的**表示**與結構檢查（[0005](0005-rust-core-document-model.md)），並定義一個與特定求解器無關的求解介面：輸入實體、約束與初始值，輸出解、剩餘自由度與診斷。求解器是此介面後方可替換的實作。
4. 求解結果是**衍生資料**：文件保存約束與驅動參數，求得的位置可重算。求解失敗時文件不進入幾何階段，並回傳可供 agent 修正的結構化診斷。
5. 求解器整合於第 3 階段實作（見 [0010](0010-migration-phases.md)）。

### 評估準則

| 準則 | 說明 |
|---|---|
| 約束涵蓋範圍 | 是否涵蓋維度階梯所需的約束種類；特別是 **port 對接是否需要 3D 約束**，還是可分解為多個 2D 草圖問題 |
| 診斷品質 | 能否指出欠約束的自由度、冗餘約束與互相衝突的約束集合，供 agent 產生修正 patch |
| 確定性 | 相同輸入是否產生相同輸出（跨平台、跨執行）；對初始值的敏感度 |
| 整合方式 | 從 Rust 呼叫的途徑（C/C++ FFI 或 WASM 執行環境）、建置複雜度、是否可同時用於桌面與瀏覽器 |
| 授權相容性 | 見下方風險；以上游 `LICENSE` 檔為準，並於評估時確認 |
| 效能 | 典型元件數量下的求解時間是否足以支援互動式編輯 |
| 維護狀態 | 上游活躍度、獨立於原應用程式使用的成熟度 |

## 考慮過的替代方案

| 方案 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| **planegcs** | 於 FreeCAD 長期實戰使用；提供多種數值演算法與冗餘／衝突診斷；已有 WASM 建置，可直接用於瀏覽器 | 僅處理 2D 草圖約束，3D port 對接需自行分解或另尋方案；原為 FreeCAD 內部元件，獨立使用的介面與文件較少；採 LGPL 授權，需處理連結方式 | 候選，待評估 |
| **SolveSpace libslvs** | 同時支援 2D 與 3D 約束；函式庫介面精簡、為嵌入而設計；已有多種語言的綁定 | 採 GPL 授權，與本專案的 MIT 授權及散佈模式有直接衝突風險，需法務判斷或以獨立程序隔離；診斷資訊相對精簡 | 候選，待評估 |
| 自行開發求解器 | 完全掌控介面與授權；可針對維度階梯最佳化 | 數值穩健性與診斷需多年累積；偏離產品重點；高風險 | 不採用 |
| 僅支援可循序求值的參數式關係（不做同時求解） | 實作簡單、完全確定、易於診斷 | 無法處理循環相依的約束；表達力不足以涵蓋一般組裝關係 | 不作為最終方案；可作為第 3 階段之前的過渡，以及求解器的前處理 |
| 以 OCCT／CadQuery 內建的組件約束求解 | 不需新增相依 | 位於 Python sidecar，違反「文件邏輯在 Rust core」的方向；約束種類與診斷有限 | 不採用 |
| 商用求解器（如 D-Cubed DCM） | 業界標準、最穩健 | 授權費用與散佈限制與開源定位不合 | 不採用 |
| 通用數值最佳化函式庫自行建模 | 彈性高、授權選擇多 | 等同自行開發求解器的大部分工作（自由度分析、診斷） | 不採用 |

## 後果

### 正面

- 取得經實戰驗證的數值穩健性與診斷能力，開發資源集中在元件模型與 agent 流程。
- 求解介面抽象化後，可在評估期間並行接上兩個候選，並保留日後更換的空間。
- 設計意圖（關係）被保存在文件中，參數修改可正確傳遞。

### 負面

- 引入 C/C++ 或 WASM 相依，建置與跨平台測試更複雜。
- 求解器的能力邊界會限制 2.0 可表達的約束種類；文件模型的約束詞彙需與所選求解器對齊。
- 最終選擇尚未確定，第 3 階段的範圍估算帶有不確定性。

### 風險與緩解

| 風險 | 影響 | 緩解措施 |
|---|---|---|
| 授權不相容（libslvs 為 GPL、planegcs 為 LGPL，本專案為 MIT） | 可能迫使整體改變授權，或無法合法散佈 | 評估階段即確認上游授權條款與版本；LGPL 以動態連結或可替換的 WASM 模組滿足要求；GPL 元件若要採用，需先取得明確的授權結論，否則不採用 |
| 2D 求解器無法表達 3D port 對接 | 維度階梯的組裝語意無法落地 | 評估時以概念文件中的代表性組裝案例作為測試；確認可否分解為「共平面 + 平面內 2D 約束」 |
| 求解結果不確定 | 相同文件在不同機器上得到不同幾何，破壞可重現性 | 固定演算法、容差與初始值策略；將求解結果隨修訂快取；跨平台比對測試 |
| 診斷不足以讓 agent 自我修正 | Agent 反覆提交無法求解的 patch | 以診斷品質為首要評估準則；在 Rust core 先做結構性的自由度預檢 |
| 上游介面變動或停止維護 | 整合層需重寫 | 固定版本並保存原始碼副本；求解介面隔離影響範圍 |

## 驗收或回顧條件

- **驗收**：
  - 完成兩個候選的對照評估報告，涵蓋上表所有準則，並以新 ADR 記錄最終選擇。
  - Rust core 的求解介面有至少一個實作通過概念文件中的代表性約束案例。
  - 欠約束、過約束與衝突三種情況都回傳結構化診斷，且不產生幾何。
  - 相同文件在三個目標作業系統上的求解結果於容差內一致。
- **回顧**：
  - 評估結論為兩者皆不適用（例如授權或 3D 能力問題）時，重新開啟替代方案。
  - 需要求解器不支援的約束種類時。
